# CyberWell RAG Chatbot — Platform Hate-Speech Policies

A retrieval-augmented generation chatbot that answers questions about major social
platforms' hate-speech and content-moderation policies, grounded strictly in an indexed
corpus of their own first-party documents. It cites the exact chunks it used, and says
plainly when the corpus doesn't have an answer — see `data/MANIFEST.md` for what's indexed
and why, and `eval/results/error_analysis.md` for how well it actually performs.

## Project structure

```
data/
  MANIFEST.md          corpus description: what it is, where it came from, doc count, question scope
  raw/                 fetched source files (not committed — see "Raw corpus" below)
  processed/           cleaned documents, chunks, and the embedding index (committed)
src/
  fetch_corpus.py      downloads data/MANIFEST.md's URLs into data/raw/
  loading.py           data/raw/ -> internal Document format (data/processed/documents.jsonl)
  chunking.py          documents -> overlapping chunks (data/processed/chunks.jsonl)
  build_index.py       chunks -> embeddings (data/processed/index.npy + index_meta.json)
  retrieval.py         retrieve(question, k) -> ranked chunks with scores + metadata
  generation.py        the prompt + grounded, cited answer
  rag.py               answer(question, k) — the entry point
eval/
  test_set.jsonl       35 questions: question, reference answer, expected chunk ids, category
  run_eval.py          runs the test set, computes hit rate@k, saves per-question results
  results/             a real evaluation run: eval_results.jsonl (graded), summary.json, error_analysis.md
api/
  app.py               Flask API
  storage.py           SQLite persistence (creates its own schema on first run)
ui/                    React + TypeScript single-page chat client
```

## Setup

**Requirements:** Python 3.12+, Node 20+, a [Gemini API key](https://aistudio.google.com/apikey).

```bash
pip install -r requirements.txt
cp .env.example .env        # then paste your key into GEMINI_API_KEY=
cd ui && npm install && cd ..
```

Environment variables (`.env`, see `.env.example`):

| Variable | Required | Default | Purpose |
| :--- | :--- | :--- | :--- |
| `GEMINI_API_KEY` | yes | — | Gemini API key for generation and embeddings |
| `CW_GEN_MODEL` | no | `gemini-flash-lite-latest` | generation model |
| `CW_EMBED_MODEL` | no | `gemini-embedding-2` | embedding model |
| `CW_TOP_K` | no | `5` | default number of chunks retrieved per question |
| `CW_DB_PATH` | no | `api/cyberwell.db` | SQLite file path (auto-created) |
| `CW_API_PORT` | no | `5000` | Flask port |
| `CW_FLASK_DEBUG` | no | off | set to `1` for Flask debug mode (off by default: it exposes tracebacks and an interactive console) |

## Running everything from a clean machine, in order

**1. Rebuild the corpus and index** (skippable — `data/processed/` is committed, so you can
jump straight to step 2 if you trust the checked-in index):

```bash
python src/fetch_corpus.py      # data/MANIFEST.md's URLs -> data/raw/ (idempotent, resumable)
python src/loading.py           # data/raw/ -> data/processed/documents.jsonl
python src/chunking.py          # -> data/processed/chunks.jsonl
python src/build_index.py       # -> data/processed/index.npy + index_meta.json (also resumable)
```

Deleting `data/processed/index.npy` and `index_meta.json` and rerunning `build_index.py`
reproduces them exactly (same model, same chunks, deterministic embeddings).

**2. Try the pipeline directly** (the entry point a reviewer would call):

```bash
python -c "from src.rag import answer; import json; print(json.dumps(answer('What is YouTube'\''s hate speech policy?'), indent=2))"
```

**3. Run the evaluation:**

```bash
python eval/run_eval.py              # full eval: retrieval metric + generated answers, for grading
python eval/run_eval.py --ablation   # k sweep (retrieval only, no generation calls)
```

`run_eval.py` is resumable: results are written per question, and a rerun skips questions
already answered successfully, so hitting a free-tier quota cap mid-run doesn't cost the
whole run. `--ablation` writes to a separate file and never touches the hand-graded results.

**4. Start the API and UI:**

```bash
python api/app.py            # Flask, port 5000
cd ui && npm run dev          # Vite, port 5173 — open the printed URL
```

## Raw corpus: why it isn't committed

`data/raw/` (52 fetched HTML files, ~49MB) is gitignored. Per the assignment's own
allowance ("if large or not redistributable, commit the fetch script instead"), it's
regenerated by `src/fetch_corpus.py` from the URLs in `data/MANIFEST.md`, which is
committed and describes exactly what's in the corpus. `data/processed/` (the cleaned text,
chunks, and embedding index derived from it — our own work product, not third-party
content, and a reasonable ~10MB) **is** committed, so a reviewer can run steps 2–4 above
immediately without needing to re-fetch 52 URLs or re-embed 868 chunks first.

## Design choices and why

- **Corpus:** 52 first-party hate-speech and moderation policy documents across Meta,
  YouTube, TikTok, X, and Reddit — chosen because a general-purpose model paraphrases these
  loosely and they change often. Several of these platforms block non-browser clients or
  render policy text client-side, so a URL that looks fine in a browser can fetch as an
  empty app shell; every entry was verified by reading its extracted text, not just its
  HTTP status. See `data/MANIFEST.md` for the inventory and its limitations.
- **Chunking:** fixed 800-character windows with 150-character overlap, splitting on
  whitespace to avoid cutting words. Chosen as a middle ground for policy prose: long
  enough to keep a rule and its qualifying clause together, short enough that a handful of
  chunks covers most single-topic questions. Trade-off found during evaluation: overlap can
  still occasionally split a heading (e.g. "Second Strike") from the sentence that follows
  it, producing a fragment that reads as complete but is subtly misattributed — see
  `eval/results/error_analysis.md`.
- **Embeddings:** `gemini-embedding-2`, with asymmetric task types — `retrieval_document`
  when indexing, `retrieval_query` when searching — so a question and a passage are each
  projected for matching the other, rather than for matching their own kind.
  `build_index.py` verifies the API returned exactly one vector per chunk before saving: a
  batched embedding call can return fewer vectors than it was given *without raising*, which
  would silently pair every chunk with another chunk's vector. It also checkpoints each
  batch and reuses vectors whose chunk text is unchanged, so a free-tier quota cap can't
  cost a whole build and adding documents costs calls proportional to what was added.
- **Vector store:** a plain NumPy array (`index.npy`) plus a parallel JSON metadata file,
  row-order matched. Meets the assignment's explicit allowance for this at this corpus
  size, and is trivial to explain.
- **Generation model:** `gemini-flash-lite-latest`, chosen for cost and speed on
  straightforward grounded QA — the hard part here is retrieval and grounding, not
  reasoning, so a larger model buys little.
- **Prompt/grounding:** the system prompt requires every claim to cite the chunk_id it came
  from, and an exact fixed sentence when the retrieved chunks don't answer the question.
  `generation.py` then parses citations back out of the answer text and filters them
  against the chunks actually retrieved, so a hallucinated citation id can never be
  reported as a source.
- **App storage:** SQLite, schema auto-created on first run (`conversations`, `messages`,
  `citations`). Simplest option that satisfies "create its own schema... given a path,"
  and easy to inspect directly. The `citations` table stores *every* retrieved chunk with
  a `cited` flag marking the ones the answer actually used, plus the chunk text — so a
  stored conversation can be replayed exactly as the user saw it, and a bad answer stays
  diagnosable afterward (you can see what the model was shown and chose to ignore, not
  just what it quoted). The turn is written only after generation succeeds, so a failed
  answer can't leave an orphaned question in the transcript.
- **Each question is answered independently** — prior turns are persisted and displayed,
  but not fed back into retrieval or the prompt. So this is a grounded question-answering
  interface with conversation history, not a chatbot that resolves "what about TikTok?"
  against the previous turn. Deliberate: carrying history into retrieval means an earlier
  question can pull the embedding away from what the user is asking *now*, and every
  answer's citations should be traceable to that question alone. Multi-turn follow-ups
  would need explicit query rewriting (resolve the pronoun into a standalone question
  first, then retrieve), which I'd add before calling it a chatbot.
- **Pipeline construction:** hand-written Python throughout, no LangChain/LlamaIndex —
  every step should be explainable without also explaining a framework's abstractions.

## Evaluation summary

35 questions (16 factual, 9 numerical, 7 comparison, 3 deliberately absent from the
corpus). Full methodology, metric definition, and per-question grades are in
`eval/results/error_analysis.md`; headline numbers:

| Metric | Value |
| :--- | :--- |
| Hit rate@5 | 0.812 |
| Abstain accuracy on absent questions | 1.0 (3/3) |
| Answer grades | 32 correct, 1 partially correct, 2 incorrect, 0 unsupported |

**Ablation — hit rate vs. k** (`python eval/run_eval.py --ablation`, retrieval only, no
generation calls):

| k | 1 | 3 | 5 | 10 |
| :--- | :--- | :--- | :--- | :--- |
| Hit rate@k | 0.531 | 0.812 | 0.812 | 0.938 |

k matters sharply at both ends and not at all in between: k=1→3 recovers 28 points (for
almost a third of questions the top-scoring chunk isn't the one with the answer), k=3→5
changes nothing, and k=10 finds another 12.6 points sitting at ranks 6–10. k=5 remains the
default because hit rate only measures whether a usable chunk was *retrieved* — doubling
context has costs the metric doesn't capture. See the error analysis for the full argument.

The error analysis surfaces four concrete findings, not just the numbers above: hit rate@k
has a blind spot for facts duplicated verbatim across many source documents (a fact can be
"missed" at its pinned chunk while being correctly retrieved and cited from an equally valid
duplicate elsewhere); cross-document comparison questions have a real retrieval gap; the
model sometimes abstains even when the right context was retrieved (won't count a fully-
listed item, won't always synthesize across two platforms); and a chunk-overlap boundary
issue found in an earlier, smaller corpus run turned out to depend on which chunk retrieval
happens to surface, not on a fixed defect. Each comes with a concrete fix-to-try.

## Known gaps and what's missing

- **Corpus composition:** 52 documents, but unevenly distributed — 20 YouTube against 6 X,
  because YouTube's help centre answers plain HTTP GETs reliably while X and Meta are only
  reachable through Wayback snapshots. The MANIFEST records every dropped URL and why.
- **Comparison-question retrieval:** a single embedded query for "compare A and B" tends to
  land between A and B in embedding space rather than close to either — see error analysis
  Finding 4. Query decomposition (retrieve once per side, merge) wasn't implemented.
- **Grading:** done by hand against the model's actual outputs (not a separate LLM-judge
  pass), so there's no judge-vs-human agreement check to report — the grades in
  `eval_results.jsonl` are the primary human judgment itself.
- **UI scope:** intentionally minimal per the assignment ("keep this part small") — a
  single conversation view, no multi-conversation history browser, no auth (as specified).
